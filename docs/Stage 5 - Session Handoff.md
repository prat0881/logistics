## ⚠️ Vocabulary — read before touching any user-facing string

**Nothing in Stage 5 is *awarded*.** Design decision **D5** locks this: *"'Approved' is provisional; term 'Awarded' is reserved for Stage 6+"* — approval selects a forwarder for a leg **with no forwarder notification**, and stays reversible until the client wins. At the end of Stage 5: no forwarder has been told anything, and the client has not accepted.

| Say this | Not this | Because |
| :-- | :-- | :-- |
| **Approved** (a leg, provisionally) | Awarded | No FF has been notified; still reversible |
| **Quotation** (the stage, the screen) | Award | The step produces and issues a client quotation |
| **Issue** a quotation | Send | `LogTransport.send()` is a no-op — nothing is transmitted yet |
| **Quoting client / Awaiting client decision** | Won | The client hasn't accepted |

`LegStatus.AWARDED` exists in the enum but is **deliberately unreachable** — reserved for the post-Won execution phase. Internal backend names (`awardSnapshot`, `LegAwardDecision`, `award.service.ts`, `AwardModule`) keep "award" and that is fine; the design itself uses them. **The rule applies to user-visible strings.**

*This was caught by the product owner on 2026-08-19: the S5.8 stage rail said "Award" and linked to the quotation screen. Fixed in `ac424f1` (label and key are now "Quotation"). Recording it here so a fresh session doesn't reintroduce it.*

### Accepted risks — carried forward, not closed
- **The B1 wedge (`leg = PENDING_APPROVAL` + `decision = DRAFT`), via a sibling-quote race (Task 5).** A pre-existing race — S5.9 strictly *shrank* its reachable-state set, it didn't introduce it. It is **not terminal** in the state-machine sense: an ordinary change-order legitimately pulls both the leg and the decision back out (the award-change-order listener resets the decision unconditionally, and both `PENDING_APPROVAL --REOPEN--> READY_FOR_RFQ` and `--INVALIDATE--> INVALID` edges exist). But it does **not self-heal** — approve/reject 409 on it, `requestRequote` can't fire the edge needed to escape it, and `sendForApproval` has no edge from `PENDING_APPROVAL` either. A human has to notice and make some qualifying edit (a field change that triggers a change-order) to clear it. Both cheap mitigations were assessed and correctly rejected: locking in-transaction can't roll back a fire that already committed, and a leg-level self-loop can't bypass a quote-level guard.
- **The second post-commit-fire wedge (`decision = PENDING_APPROVAL` + `leg = FULLY_QUOTED` + `quote = QUOTED`), added by the final whole-branch review. CLOSED by S5.9.2 (Q5) — see that section below.** `sendForApproval` commits its transaction and only then fires the quote and leg transitions. ### Q1/Q2 — a re-quote now walks the leg (and the query) back honestly. Closes register C7 for every re-quote from this deploy onward.
Asking a forwarder to revise a price used to move neither the leg nor the query: a leg could sit at `FULLY_QUOTED` — or a query at `QUOTED` — while its only price was in fact back out for a re-quote. Two new leg edges (`FULLY_QUOTED --requote.partial--> PARTIALLY_QUOTED`, `FULLY_QUOTED | PARTIALLY_QUOTED --requote.outstanding--> RFQ_SENT`, both `kind: "reopen"`) let `LegQuoteProjector` walk a leg *backwards* on a genuine re-quote — narrowly: only when the triggering quote event itself carries `requoteTriggered === true` (read off the transition that just committed, not off a scan of the quote row, which a concurrent change could already have moved past), and only from `FULLY_QUOTED`/`PARTIALLY_QUOTED` (the never-walk-backwards backstop is untouched for every other event). A third edge, not in the brief's literal list but reachable and needed to avoid an `IllegalTransitionError`, covers `PARTIALLY_QUOTED --requote.outstanding--> RFQ_SENT` (re-quoting the one comparable offer on an already-partial leg). The `APPROVED` path — a winner's own quote re-quoted after approval — needed a second door: `NegotiationService.requestRequote`'s `REOPEN_AWARD` fire pulls the leg out of the projector's `ROLLUP_FROZEN` state via a different event the quote-status listener doesn't hear, so a narrow `recomputeAfterRequote` entry point discharges the same rule from the caller side.

**What "closes C7" does NOT mean — this ships to a live production database (final whole-branch review).** The backward walk fires only on a *new* re-quote event. **Nothing walks an existing leg back at deploy time.** A leg already sitting in the C7 shape right now — `FULLY_QUOTED` while carrying a `REQUOTED` quote — keeps reading **"Fully Quoted"** (and its query keeps reading "Quoted") until that forwarder re-submits, the RFQ expires, or something else moves the leg. So C7 is closed **going forward**, not backfilled: no migration, no sweep, and none was written on purpose (there is no schema change in this sub-build, and a status backfill would have to fire through `StatusService` per leg to keep the transition log honest). If any such leg exists in prod when this deploys, expect it to keep misreporting until it resolves itself the ordinary way.

**No query-level code change was needed.** `deriveQueryStatus` already maps both `RFQ_SENT` and `PARTIALLY_QUOTED` to `QueryStatus.RFQ_SENT` through the same case fallthrough, so the query follows the leg for free once the leg genuinely walks back — verified end-to-end in the new e2e suite, not assumed.

**The product-visible consequence, worth surfacing on purpose:** a query with one `APPROVED` leg and one re-negotiated leg now reads **`RFQ_SENT`**, not `QUOTED` — the query-status rule is "least-advanced leg wins," and that is the correct derivation. But it means asking a single forwarder to sharpen a single leg's price drops the **whole query** two rungs in the query list, even though nothing else on that query changed. Not a defect; a consequence the product owner should hear stated plainly rather than discover live.

### Q3 — the send/approve guard, its third rewrite
This guard has now been rewritten three times, and it's worth recording precisely why, because the shape of the first two failures is the shape most likely to repeat. **Rewrite 1** was S5.9's original build: it passed its own task-scoped review, then S5.9's whole-branch review caught a Critical (documented above, in that section's C1) — a leg sent through A9's "proceed without waiting" hatch could never be approved, and rejecting it made things worse. The fix (`isFullyQuotedForDecision`, consulting the immutable `StatusTransition` row the send itself wrote) held until this round. **Rewrite 2** was this round's own first pass at widening that guard for Q1: it closed the immediate breakage (a re-quoted leg failing to *send* at all) but, in doing so, left a second dead end on the arm the first fix never covered — a leg legally sent through A3's *deadline-passed* arm (every outstanding RFQ window closed, no re-quote in play) still could never be approved. `reject → re-send → approve` loops forever, breakable only by the expiry cron (and not at all for an `INVALID` sibling, which has no expire edge). That was caught inside this task's own review round, before it could reach anything broader — the implementer's own test had enshrined the loop as *intended behaviour* rather than flagging it as a gap.

**Rewrite 3, the current state, states the rule plainly:** *a leg is approvable iff it is fully quoted, OR its send was legally permitted.* `sendForApproval` now records **which arm of A3 permitted the send** — the fact itself (`from = FULLY_QUOTED`) when the leg genuinely was fully quoted, A9's own recorded reason when the override carried it, or a fixed sentinel string when A3's deadline-passed arm carried it — on the send's **own** `StatusTransition` row, whenever the leg was not fully quoted at send. `approve` ORs that recorded permission in as a third, independent term (short-circuiting after the cheap live-rollup check); `reject` deliberately excludes it, so a fallen-back leg always returns to `PARTIALLY_QUOTED` and never a promoted `FULLY_QUOTED`. The totality that makes the invariant hold — the permission is non-null *whenever* the leg wasn't fully quoted at send — is by construction, not inference: it deliberately doesn't have `approve` re-derive A3's verdict later, which can't work (a re-quote pushes RFQ deadlines days out, and an `INVALID` sibling has no expire edge, so the identical question asked minutes later can answer differently, or not at all).

**The known fragility, on the record rather than assumed away:** the permission is a **convention on a free-text column** (`StatusTransition.reason`), not a typed field — `approve` reads a string to decide whether an approval is allowed. It is exact today because there is exactly one writer (`sendForApproval` is the only call site in the codebase that fires `SEND_FOR_APPROVAL`, grepped across all three packages) and the lookup is narrowed by both the event and the destination status, so nothing else can accidentally mint a permission. But nothing at the type level stops a future contributor from writing a reason into that same slot for an unrelated purpose and silently widening what `approve` will accept. The reviewer tried three separate ways to break the marker and could not (specific mutations are in the ledger); the fragility is structural, not a live bug.

**The A9/A3 matrix was re-walked afterward, row by row.** Only **row 7** — the A3 deadline-passed arm, the hole this rewrite closes — changed approve's outcome. An earlier draft of the implementer's own report also claimed row 15 changed; that was **wrong, and has been corrected in the ledger**: row 15's approve already returned 200 before this fix, carried by the live rollup — only *which term* carries it changed. If you go looking at the matrix in the SDD ledger, trust the corrected version, not the first one.

### Q5 — rejection is always possible
`reject()` used to 409 outright when the shortlisted quote had drifted off `PENDING_APPROVAL` — which made the leg unrecoverable, since `approve`'s own guard refused it for the identical reason. Now `reject` **tolerates** the drift on **both** entities it fires at:
- **the quote** (Q5's original half): when the shortlisted quote isn't `PENDING_APPROVAL` (drifted to `QUOTED`, to `REQUOTED`, or missing entirely), it skips that quote's own `RETURN` fire, logs at warn, and carries on — the decision still writes to `DRAFT` with the reason, and the leg still returns to its correctly recomputed rollup status;
- **the leg** (added by the final whole-branch review, IMPORTANT 1): when the leg itself isn't `PENDING_APPROVAL` — which is exactly the registered wedge's shape, since a leg that never got its own send fire never left `FULLY_QUOTED` — it skips the leg's `RETURN_FULL`/`RETURN_PARTIAL` fire the same way and for the same reason. A leg that never left its rollup status has nothing to be returned to; every other effect of the rejection (the `DRAFT` write, the reason, the `REJECT` event, the executive notification) still runs.

Rejection is the recovery path; it must not require the thing being recovered from to already be healthy — and it must not 500 on it either.

This **closes the registered second wedge** (see "Accepted risks carried forward" above — `decision = PENDING_APPROVAL` / `leg = FULLY_QUOTED` / `quote = QUOTED`, reachable when a post-commit quote fire throws). That wedge was previously recorded as self-healing (an unrelated change-order eventually resets the decision) rather than actually fixed. **Read that entry, not this summary, for the full correction**: Q5 as first shipped did *not* close it — it 500'd on that exact triple, which is what the final review caught and the leg-fire guard above fixes. It is closed now, mutation-proven, by a test that seeds the triple directly.

## Reusable facts (learned across S5.4/S5.5 SDD)
- Caller id = `user.userId` (`RequestUser`); e2e actor `@db.Uuid` cols need cookie `sub: randomUUID()`.
- Every owned status change via `StatusService.fire` (awaits `emitAsync` → projectors run in-fire → **every new `@OnEvent` listener MUST try/catch+log** or it fails the caller). Query status is a projection (never `fire`d).
- Clear a `Json?` column with **`Prisma.DbNull`** (plain `null` sets JSON-null, still truthy).
- Local Postgres :5433 (`svyft-postgres-task4`); `set -a; . apps/api/.env; set +a` before prisma/jest.
- Rebuild `@svyft/shared` after editing it; run `pnpm run typecheck` per task (vitest/jest don't type-check).
- **(S5.9)** A `StatusService.fire` call MUST happen **after** an outer transaction commits, never inside one that holds a row lock on the same row `fire` needs — `fire` opens its own transaction on a different pool connection, so firing from inside a lock-holding transaction self-deadlocks until Prisma's 5s interactive-transaction timeout (P2028).
- **(S5.9)** To serialize two HTTP-triggered mutations that must not race on the same row, take the **same** `SELECT … FOR UPDATE` lock, in the same order, in both call paths — mutual exclusion is a property of the shared lock helper (`lockLeg`), not of either caller individually, and needs no dedicated concurrency test once that's true.
- **(S5.9)** A plain function component (no `forwardRef`) silently breaks under Radix's `asChild`/`Slot` pattern — React drops the ref with only a dev-console warning, not a crash, so it can ship unnoticed. Any `components/ui/*` primitive that might become a `TooltipTrigger`/`PopoverTrigger`/etc. child should be `forwardRef` from the start (`Button` already was; `Badge` wasn't, until S5.9 T10).
